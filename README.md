# Lab02. Путь программы: IL, HEX и Debug vs Release

## Результаты замера Debug vs Release

Измерялось время выполнения `SumTo(1_000_000_000)` в миллисекундах.

| Режим   | Запуск 1 | Запуск 2 | Запуск 3 | Запуск 4 | Запуск 5 | Минимум |
| ------- | -------: | -------: | -------: | -------: | -------: | ------: |
| Debug   |      1971 |      1963 |      1970 |      1980 |      1971 |     1963 |
| Release |      359  |      495  |      495  |      443  |      412  |     420  |

В моём эксперименте Release оказался быстрее Debug примерно в 5,4 раз.

## Что я обнаружил при сравнении IL
1. в Debug присутствуют инструкции `nop`, которых нет в Release;
2. в Debug метод `Add()` содержит блок `.locals init (...)` с двумя локальными переменными, в Release его нет;
3. в Debug результат сначала сохраняется в локальную переменную и тут же читается обратно (`stloc` / `ldloc`), в Release этих операций нет;
4. в Debug есть безусловный переход `br.s` на следующую инструкцию, в Release его нет;
5. количество IL-инструкций в методе `Add()` изменилось с 10 до 4 (размер кода 11 → 4 байта);
6. размер кода `SumTo()` уменьшился с 36 до 22 байт, локальных переменных стало 2 вместо 4 (исчезли лишние `bool` и `int64`);
7. условие цикла в `SumTo()` в Release проверяет одна инструкция `ble.s`, а в Debug для этого нужна цепочка `cgt`, `ldc.i4.0`, `ceq`, `stloc.2`, `ldloc.2`, `brtrue.s`.

## Ответы на контрольные вопросы

**1. Что такое IL и зачем он нужен между C# и машинным кодом?**

IL (Intermediate Language) - промежуточный байт код, в который компилятор Roslyn превращает C# программу. Он хранится в сборке (.dll/.exe) вместе с метаданными о типах и методах. IL не привязан к конкретному процессору, поэтому одна и та же сборка может запускаться на разных платформах и архитектурах (например, x86-64 и ARM): при запуске JIT-компилятор переводит нужные методы в машинный код конкретного процессора и может учитывать его возможности.

**2. Почему .dll можно декомпилировать?**

Потому что в .NET сборке лежит не готовый машинный код, а IL и метаданные: имена типов, методов, сигнатуры и т. д. IL достаточно высокоуровневый, и по нему декомпилятор (например, ILSpy) может восстановить код, очень похожий на исходный. Если рядом есть .pdb с отладочной информацией, восстановить можно ещё точнее (например, имена локальных переменных).

**3. Какие отличия Debug и Release вы увидели в IL?**

В Debug-версии метода `Add()` есть `nop`, блок `.locals init` с лишними локальными переменными, пара `stloc`/`ldloc` (сохранить результат в переменную и сразу прочитать обратно) и `br.s` на следующую инструкцию. В Release всё это убрано, остались только `ldarg.0`, `ldarg.1`, `add`, `ret`, поэтому IL стал короче (было 10 инструкций, стало 4).В `SumTo()` Release тоже компактнее: код занимает 22 байта вместо 36, а локальных переменных две вместо четырёх.

**4. Почему Release обычно быстрее Debug?**

В Release компилятор применяет больше оптимизаций и убирает лишние промежуточные операции, а JIT тоже оптимизирует генерируемый машинный код. В Debug оптимизаций меньше, чтобы программу было удобно отлаживать (пошагово выполнять, смотреть значения переменных). Но это «обычно», а не гарантия: результат зависит от кода, версии .NET, JIT и процессора. Поэтому производительность сравнивают на Release, а разницу измеряют, а не угадывают.

**5. Почему строковый пароль в .dll нельзя считать защищённым?**

Строковые литералы хранятся в сборке как обычный текст (UTF-16) без шифрования, их можно найти в HEX-редакторе, а ILSpy покажет их прямо в декомпилированном коде. Сам факт компиляции ничего не скрывает. Пароли, API-ключи и другие секреты не нужно хранить в коде программы.
